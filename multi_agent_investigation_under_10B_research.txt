NGHIÊN CỨU BÀI TOÁN
MULTI-AGENT ORCHESTRATION & INVESTIGATION PIPELINE
Giới hạn mô hình: <= 10B tham số
Ngày nghiên cứu: 2026-09-25

======================================================================
0. EXECUTIVE SUMMARY
======================================================================

Bài toán trong ảnh không nên được giải theo kiểu "cho 5 agent nói chuyện tự do với nhau".
Với giới hạn model <=10B, cách có xác suất thành công cao hơn là:

  Deterministic workflow / state machine
        +
  một model nhỏ dùng lại cho nhiều role
        +
  evidence store bất biến
        +
  entity-resolution hybrid
        +
  schema validation + constrained output
        +
  rule engine cho các quyết định có thể xác định bằng logic
        +
  LLM chỉ xử lý phần semantic/ambiguous.

Kiến trúc nên là hierarchical supervisor nhưng supervisor KHÔNG nhất thiết phải là LLM.
Supervisor nên ưu tiên code/rules để:
- phân rã task theo template,
- giới hạn tool budget,
- theo dõi state,
- dừng pipeline,
- retry khi schema lỗi,
- kiểm tra evidence coverage.

LLM <=10B nên được dùng cho:
1) semantic extraction,
2) entity-match tie breaker,
3) conflict interpretation,
4) synthesis/final explanation,
5) tool selection khi route không thể xác định bằng rule.

Đề xuất model:
- Default: Qwen3-8B (open-weight, tool calling, multi-step tool use).
- Alternative rất đáng thử: Ministral 3 8B (structured output + function calling chính thức).
- Nhẹ hơn: Gemma 3 4B / Qwen2.5-7B nếu hạ tầng hoặc VRAM hạn chế.

Đề xuất stack:
- Python + Pydantic
- LangGraph hoặc workflow engine tự viết
- FastMCP / MCP SDK
- DuckDB/PostgreSQL
- Splink hoặc pyJedAI cho entity resolution
- sentence-transformers / embedding nhỏ cho blocking
- vLLM hoặc SGLang cho inference
- JSON Schema + retry tối đa 1-2 lần
- pytest + benchmark harness riêng.

Kết luận quan trọng:
"Multi-agent" ở đây nên hiểu là tách vai trò và contract, KHÔNG phải bắt buộc dùng nhiều model.
Một model Qwen3-8B có thể đóng Supervisor, Extractor, Resolver, Verifier, Narrator với system prompt
khác nhau; nhưng càng nhiều bước có thể thay bằng deterministic code càng tốt.

======================================================================
1. BẢN CHẤT BÀI TOÁN
======================================================================

Loại bài toán:
Multi-Agent Orchestration & Investigation Pipeline với evidence-based reasoning.

Các năng lực cốt lõi:

A. Orchestration
- phân rã câu hỏi thành các bước điều tra,
- chọn worker,
- quản lý dependency giữa các subtask,
- quản lý tool budget,
- termination condition,
- retry/fallback.

B. Entity Resolution
- từ dữ liệu không hoàn hảo, xác định các record có cùng thực thể hay không.
Ví dụ:
  "Nguyen Van A", "N. V. A.", customer_id X, phone bị che, địa chỉ gần giống
  -> có phải cùng khách hàng không?

C. Evidence/Provenance
Mọi conclusion phải truy ngược được:
  claim -> evidence_id -> tool call -> raw source.

D. Conflict Resolution
Ví dụ:
  customer: "chưa nhận hàng"
  logistics event: "delivered"
  proof of delivery: thiếu
  seller: "đã giao cho carrier"
Hệ thống không được đơn giản chọn một nguồn rồi kết luận.
Nó phải biểu diễn:
  - các claim cạnh tranh,
  - evidence ủng hộ/phản bác,
  - độ tin cậy,
  - freshness,
  - unresolved uncertainty.

E. Constraint Satisfaction
Output phải thỏa:
- JSON Schema,
- logic consistency,
- tool budget,
- evidence coverage,
- không hallucinate evidence,
- không reference evidence_id không tồn tại.

======================================================================
2. "KẾT QUẢ TỐT" NÊN ĐƯỢC ĐO NHƯ THẾ NÀO?
======================================================================

Không nên chỉ chấm final answer bằng BLEU/ROUGE hoặc cảm tính.

Nên tách metric:

2.1 Entity Resolution
- Precision
- Recall
- F1
- False Merge Rate (rất quan trọng)
- False Split Rate
- Candidate Recall sau blocking

False merge thường nguy hiểm hơn false split trong investigation:
ghép nhầm hai người/thực thể có thể làm hỏng toàn bộ reasoning downstream.

2.2 Evidence Grounding
- Evidence Precision:
  % evidence được cite thực sự hỗ trợ claim.
- Evidence Recall:
  % claim quan trọng có evidence.
- Citation Validity:
  evidence_id có tồn tại hay không.
- Unsupported Claim Rate:
  % claim không có provenance.

Mục tiêu MVP tốt:
- Citation validity = 100%
- Unsupported high-severity claim = 0%

2.3 Conflict Resolution
- Conflict detection recall
- Correctly unresolved rate:
  hệ thống phải biết khi nào chưa đủ bằng chứng.
- Contradiction leakage:
  final answer không được chứa đồng thời hai kết luận không thể cùng đúng mà không giải thích.

2.4 Tool Use
- Tool selection accuracy
- Invalid tool-call rate
- redundant calls / case
- total tool calls / case
- tool failure recovery rate

2.5 Structured Output
- JSON parse success
- schema validation success
- semantic consistency validation success
- retry count

Mục tiêu:
- JSON parse >= 99%
- schema valid >= 99%
sau repair/retry layer.

2.6 End-to-end
- Case accuracy
- Evidence-grounded answer accuracy
- Average latency
- tokens/case
- tool calls/case
- % cases requiring human review.

======================================================================
5. NGUYÊN TẮC VÀNG: DÙNG LLM ÍT NHẤT CÓ THỂ
======================================================================

Một pipeline tốt với <=10B thường thắng bằng hệ thống chứ không phải prompt.

Ví dụ:

KHÔNG:
"Agent, hãy xem 10,000 customer records và tìm người giống nhất."

NÊN:
1. normalize tên/email/phone/address bằng code,
2. deterministic match các exact identifiers,
3. blocking lấy top 20-50 candidates,
4. fuzzy/embedding/probabilistic score,
5. chỉ gửi top 3-5 ambiguous candidates vào LLM.

LLM chỉ giải quyết entropy còn lại.

Cùng nguyên tắc cho conflict:
- timestamps => code,
- source type => rules,
- numeric comparison => code,
- logical contradictions => validator,
- semantic contradiction => LLM.

======================================================================
6. ENTITY RESOLUTION: PIPELINE CÓ XÁC SUẤT THẮNG CAO
======================================================================

Entity Resolution truyền thống thường có 2 stage:
1) blocking
2) matching

Đây vẫn là thiết kế đúng cho LLM system.

6.1 Normalize

Ví dụ:
- lowercase,
- unicode normalize,
- bỏ punctuation,
- chuẩn hóa phone,
- chuẩn hóa email,
- chuẩn hóa địa chỉ,
- tokenize tên,
- canonicalize abbreviations.

6.2 Exact / deterministic keys

Ưu tiên:
- unique customer ID
- verified email
- verified phone
- transaction ID
- order ID
- tracking ID.

Nếu exact verified ID match -> không cần LLM.

6.3 Blocking

Tạo candidate list nhỏ bằng:
- cùng ZIP / state,
- phonetic/fuzzy name,
- email domain + partial local part,
- phone suffix,
- embedding nearest neighbors,
- BM25,
- learned blocking.

Splink nhấn mạnh blocking là yếu tố quyết định performance của linkage pipeline.

6.4 Probabilistic scoring

Dùng Splink/Fellegi-Sunter hoặc lightweight classifier.

Features:
- name_similarity
- address_similarity
- phone_match
- email_match
- geo_distance
- temporal compatibility
- account overlap
- order overlap.

Ví dụ:
score >= 0.98 -> MATCH
score <= 0.10 -> NO_MATCH
0.10 < score < 0.98 -> ambiguous -> LLM judge

Threshold phải tune trên validation set, không lấy tùy ý.

6.5 LLM tie-breaker

Chỉ đưa:
- entity A
- top candidate B1/B2/B3
- normalized fields
- deterministic feature scores
- explicit conflict fields.

Prompt yêu cầu output:
{
  "decision": "MATCH|NO_MATCH|UNCERTAIN",
  "candidate_id": "...",
  "supporting_fields": [...],
  "conflicting_fields": [...],
  "confidence": 0.0-1.0
}

Quan trọng:
LLM confidence KHÔNG được coi là calibrated probability.
Dùng nó làm tín hiệu phụ, không phải truth.

6.6 Benchmark entity resolution

Dataset/repo đáng dùng:
- ER-Magellan / DeepMatcher datasets
- Ditto
- Machamp
- WDC Product Matching
- Splink synthetic datasets
- pyJedAI demos

Ditto cho thấy cách serialize pair record thành sequence-pair classification.
Machamp có benchmark structured, semi-structured, heterogeneous schema.
Đây là nguồn thực nghiệm tốt hơn việc chỉ prompt LLM.

7. EVIDENCE MODEL / PROVENANCE
======================================================================

Không cho agent viết conclusion trực tiếp từ raw tool output rồi mất dấu nguồn.

Mỗi tool result phải được materialize thành EvidenceRecord:

EvidenceRecord:
{
  "evidence_id": "ev_001",
  "source": "logistics_api",
  "source_type": "system_record",
  "retrieved_at": "...",
  "event_time": "...",
  "entity_ids": ["order_123", "customer_7"],
  "content": {...},
  "content_hash": "...",
  "tool_call_id": "tc_009"
}

Claim:
{
  "claim_id": "cl_014",
  "subject": "order_123",
  "predicate": "delivery_status",
  "value": "delivered",
  "evidence_for": ["ev_001", "ev_007"],
  "evidence_against": ["ev_010"],
  "status": "CONTESTED"
}

Final answer không được reference raw source tự do.
Chỉ được reference evidence_id tồn tại trong store.

Verifier:
for every final_claim:
    assert len(evidence_for) > 0
    assert all(eid in evidence_store)
    assert no forbidden contradiction

Đây là cách ngăn "bịa evidence" hiệu quả hơn prompt.

======================================================================
8. CONFLICT RESOLUTION
======================================================================

Không nên có rule đơn giản:
"system log luôn đáng tin hơn customer".

Nên tách 4 khái niệm:

1. Source reliability
2. Evidence directness
3. Temporal freshness
4. Claim compatibility

Ví dụ:

Customer says "I did not receive package"
-> direct evidence về customer experience,
   nhưng không xác minh được physical delivery.

Carrier status "delivered"
-> system event,
   nhưng có thể scan nhầm hoặc giao sai người.

Proof-of-delivery signature/photo
-> direct physical evidence mạnh hơn.

Nên tạo conflict object:

{
  "conflict_id": "...",
  "claim_a": "...",
  "claim_b": "...",
  "type": "STATUS_CONTRADICTION",
  "resolution": "UNRESOLVED|A_WINS|B_WINS|MERGED",
  "required_next_evidence": [...]
}

Resolution policy:

A. Nếu conflict có thể giải bằng timestamp:
   dùng deterministic temporal logic.

B. Nếu nguồn khác nhau nói về khác giai đoạn:
   cả hai có thể đúng.
Ví dụ:
   status at 10:00 = in_transit
   status at 15:00 = delivered.

C. Nếu cùng thời điểm và mutually exclusive:
   tìm stronger direct evidence.

D. Nếu vẫn không đủ:
   output UNRESOLVED và đề nghị next tool/evidence.

"Biết chưa đủ bằng chứng" là behavior đúng, không phải failure.

======================================================================
9. SUPERVISOR: LLM HAY CODE?
======================================================================

Với <=10B:
Supervisor nên HYBRID.

Rule-based supervisor xử lý:
- state transitions,
- budget,
- retry,
- termination,
- mandatory steps,
- validation.

LLM supervisor chỉ xử lý:
- query classification,
- task decomposition khi query mới lạ,
- chọn một trong số route hợp lệ.

Ví dụ state machine:

INIT
 -> IDENTIFY_ENTITIES
 -> COLLECT_EVIDENCE
 -> RESOLVE_ENTITIES
 -> BUILD_CLAIMS
 -> CHECK_CONFLICTS
 -> VERIFY
 -> FINALIZE

Nếu VERIFY trả:
MISSING_EVIDENCE
 -> COLLECT_EVIDENCE(targeted)

Nếu TOOL_BUDGET_EXCEEDED
 -> HUMAN_REVIEW / PARTIAL_RESULT

Điều này tốt hơn "agent tự quyết định cứ làm tiếp hay dừng".

10. AGENT ROLES TỐI GIẢN
======================================================================

Không cần 10-20 agent.

MVP nên có 5 logical roles:

1. Coordinator
- lập kế hoạch,
- route worker,
- giữ budget.

2. Evidence Collector
- gọi MCP tools,
- normalize tool result,
- tạo EvidenceRecord.

3. Entity Resolver
- blocking + scorer + LLM tie-breaker.

4. Investigator / Conflict Resolver
- xây claim graph,
- tìm contradiction,
- yêu cầu targeted evidence.

5. Verifier + Narrator
- verifier nên phần lớn deterministic.
- narrator chỉ viết từ verified state.

Có thể tách Narrator thành agent 6 nếu cần.

Một physical model Qwen3-8B có thể phục vụ tất cả các logical roles.

12. MCP TOOLING
======================================================================

MCP giúp standardize tool/resource access nhưng MCP không tự giải quyết:
- grounding,
- authorization,
- tool safety,
- evidence provenance,
- retry semantics.

Mỗi MCP tool wrapper nên trả kết quả dạng:

{
  "tool_call_id": "...",
  "tool_name": "...",
  "status": "OK|ERROR|PARTIAL",
  "records": [...],
  "source_metadata": {...}
}

Không feed raw HTML/log 100KB trực tiếp cho LLM.
Nên có adapter:
raw tool output -> normalize -> filter -> evidence records -> LLM.

Tool budget nên cứng:
- max_total_calls
- max_calls_per_tool
- max_retries
- max_parallel_calls
- max_payload_tokens.

Ví dụ MVP:
- max 8 tool calls/case
- max 1 retry/tool
- max 3 candidates/entity
- max 2 replans.

======================================================================
13. JSON SCHEMA / CONSTRAINED OUTPUT
======================================================================

Small model thường fail pipeline không phải vì reasoning kém mà vì:
- thừa text,
- sai field,
- enum sai,
- malformed JSON,
- thiếu required property.

Do đó:
1. dùng JSON Schema/Pydantic model,
2. constrained decoding nếu server hỗ trợ,
3. validate,
4. repair deterministically nếu trivial,
5. retry model một lần với validation error,
6. fail closed nếu vẫn sai.

Không nên retry vô hạn.

Ví dụ:

class Resolution(BaseModel):
    decision: Literal["MATCH","NO_MATCH","UNCERTAIN"]
    candidate_id: str | None
    supporting_evidence_ids: list[str]
    conflicting_evidence_ids: list[str]

Sau parse:
- evidence_id có tồn tại?
- candidate_id có trong candidate list?
- MATCH mà candidate_id null -> invalid.
- UNCERTAIN nhưng confidence=1.0 -> semantic warning.

Structured output từ Mistral hỗ trợ custom schema;
Qwen3 tool-call output cũng có structured tool format nhưng vẫn nên validate ở app layer.

======================================================================
14. PROMPTING CHO SMALL MODEL
======================================================================

Prompt càng "văn chương" càng không tốt.

Nên:
- role ngắn,
- input format cố định,
- output schema cụ thể,
- 2-4 examples khó,
- nói rõ forbidden behavior,
- không yêu cầu chain-of-thought.

Ví dụ Entity Resolver system prompt:

"You are an entity-resolution judge.
You receive ONE source entity and up to THREE candidates.
Use only supplied fields and scores.
Never invent identifiers.
Return MATCH only when evidence is sufficient.
If evidence is conflicting or insufficient, return UNCERTAIN.
Output only schema X."

Đưa cả 50 policy rule vào một prompt thường làm model 7-8B giảm reliability.
Policy nên đặt trong code validator.

======================================================================
15. CLAIM GRAPH THAY VÌ CHAT HISTORY
======================================================================

Không dùng conversation history làm database.

Dùng graph / relational state:

Entity nodes
Claim nodes
Evidence nodes

Edges:
- evidence SUPPORTS claim
- evidence CONTRADICTS claim
- claim ABOUT entity
- entity SAME_AS entity
- entity POSSIBLY_SAME_AS entity

Narrator chỉ nhận:
- verified claims,
- unresolved conflicts,
- minimal evidence snippets.

Không nhận toàn bộ raw logs.

Đây là pattern tương tự một Kaggle Agentic Investigation Board:
Researcher -> Extractor -> Merger -> Narrator,
trong đó vector search thu hẹp candidate trước khi LLM quyết định merge.
Ý tưởng này rất hợp với constraint <=10B.

16. KAGGLE: CÓ AI LÀM GẦN BÀI NÀY CHƯA?
======================================================================

Có các Kaggle capstone/writeup rất gần về kiến trúc, nhưng không nên mặc định tác giả là "Kaggle Master"
nếu profile/rank không được xác minh.

A. Agentic Investigation Board (Kaggle, 2026)
Rất gần bài toán:
- Orchestrator
- Researcher
- Extractor
- Merger
- Narrator
- MCP
- entity extraction
- candidate narrowing bằng vector index
- evidence board
- cited narrative
- giới hạn replan

Ý tưởng đáng lấy:
1) candidate generation bằng math/vector trước LLM;
2) LLM chỉ xét vài candidate;
3) narrator chỉ đọc structured graph cuối;
4) không để context tăng theo toàn bộ evidence;
5) replan target cụ thể thay vì restart toàn bộ.

B. IncidentZero-AI (Kaggle, 2026)
Điểm cực đáng lấy:
- tách deterministic detection và LLM reasoning.
- rule engine tìm evidence thật;
- LLM đứng trên evidence đã verify;
- tránh việc LLM "phát hiện" dữ liệu không tồn tại.

Đây chính xác là pattern nên dùng:
verified evidence first, generation second.

C. Veritas AI / Smart Personal Research Assistant
Cho thấy:
- multi-agent sequential pipeline,
- tool use,
- citations,
- evaluation / judge,
- memory.

Nhưng cần cẩn thận với LLM-as-a-Judge:

Đối với entity resolution và tool correctness, có thể dùng exact labels/unit tests.

Tóm lại:
Có prior art trên Kaggle đáng tham khảo, nhưng giá trị nằm ở architecture và writeup,
không nằm ở danh hiệu của tác giả.

26. PSEUDOCODE END-TO-END
======================================================================

def investigate(query):

    state = init_case(query)

    intent = classify_intent(query)

    plan = build_plan(intent)

    while not state.done:

        step = deterministic_router(state, plan)

        if step == "collect":
            result = call_next_tool(state)
            evidence = normalize_to_evidence(result)
            evidence_store.add(evidence)

        elif step == "entity_resolution":
            candidates = blocking(state.entities)
            scores = probabilistic_score(candidates)

            ambiguous = select_ambiguous(scores)

            if ambiguous:
                llm_result = llm_entity_judge(ambiguous)
                validate_schema(llm_result)

            update_entities(...)

        elif step == "claims":
            build_claim_ledger_from_evidence()

        elif step == "conflicts":
            conflicts = deterministic_conflict_scan()

            for semantic_conflict in unresolved:
                result = llm_conflict_classifier(...)
                validate_schema(result)

        elif step == "verify":
            errors = verify_case(state)

            if not errors:
                state.done = True

            elif can_retrieve_more(errors) and state.budget > 0:
                add_targeted_tool_steps(errors)

            else:
                state.done = True
                state.requires_human = True

    final = narrator(verified_case_view(state))
    validate_final(final)

    return final

27. VERIFIER NÊN KIỂM TRA GÌ?
======================================================================

Hard checks:
[ ] all evidence IDs exist
[ ] all entity IDs exist
[ ] all tool names allowed
[ ] no call exceeds budget
[ ] final JSON validates
[ ] required fields present
[ ] timestamps parsable
[ ] no impossible temporal ordering
[ ] no high-severity claim without evidence
[ ] no resolved conflict without resolution evidence
[ ] no candidate outside candidate list selected.

Soft checks:
[ ] suspicious confidence
[ ] source too stale
[ ] only one weak source
[ ] semantic contradiction
[ ] insufficient evidence diversity.

Nếu hard check fail:
NO FINAL SUCCESS.

28. FAILURE MODES CẦN DỰ ĐOÁN
======================================================================

1. Agent hallucinated evidence_id
Fix:
evidence IDs chỉ được chọn từ enum/list hiện có + validator.

2. Agent gọi sai tool
Fix:
route bằng rules trước, LLM chỉ khi ambiguous.

3. Tool result quá dài
Fix:
adapter + evidence extraction trước LLM.

4. Entity merge nhầm
Fix:
blocking + probabilistic scoring + conservative threshold.

5. "LLM confidence = 0.95" nhưng sai
Fix:
không coi self-confidence là calibrated probability.

6. Infinite loop
Fix:
hard tool budget + max replan + explicit termination.

7. Multi-agent context explosion
Fix:
state ngoài LLM, chỉ gửi task-local context.

8. Narrator thêm chi tiết không có trong state
Fix:
narrator chỉ nhận verified claim graph, verifier scan output.

9. Conflict bị "ép" phải chọn bên thắng
Fix:
cho phép UNRESOLVED.

10. JSON đôi lúc lỗi
Fix:
constrained output + schema + one retry.

- candidate set nhỏ,
- context nhỏ,
- schema rõ,
- task một nghĩa,
- deterministic logic bên ngoài,
- evidence bắt buộc,
- retry hữu hạn,
- state machine,
- benchmark có ground truth.

          deterministic supervisor
                   |
       +-----------+-----------+
       |                       |
   MCP/evidence             ER engine
       |                block -> score
       |                       |
       +---------> LLM tie-breaker
                   |
              claim ledger
                   |
             conflict engine
                   |
                verifier
                   |
             Qwen3-8B narrator

Nếu phải chọn một hướng để bắt đầu:
1) Qwen3-8B,
2) LangGraph hoặc state machine tự viết,
3) Splink + RapidFuzz/embedding cho ER,
4) Pydantic schema,
5) MCP mock services,
6) evidence ledger,
7) 100-case benchmark trước khi làm UI.
